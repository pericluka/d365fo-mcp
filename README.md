# d365fo-mcp

An MCP server that lets Claude talk to Dynamics 365 Finance and Operations through OData. It works on any F&O environment that exposes the OData endpoint, including the LCS VHD one-box, cloud-hosted dev boxes and Tier 2+ environments. It needs no Power Platform, Copilot Studio or Copilot credits.

It runs in two ways with the same six tools:

- **Local** (`dist/index.js`): Claude Code or Claude Desktop starts it on your machine and every call runs as one F&O service user, authenticated with a client secret. Set up in about half an hour, see Setup.
- **Remote** (`dist/http.js`): hosted once, reachable from claude.ai, Claude Desktop and Claude Code over HTTPS. Every user signs in with their own Entra account and F&O applies that user's security roles. See Remote server.

As of October 2026 Microsoft also ships a [Dynamics 365 ERP MCP server](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/copilot/copilot-mcp). It runs on Tier 2+ environments and Unified Developer Environments. It works in the user's security context and can drive forms and X++ actions besides reading data. An admin has to approve every client on an allowlist. Outside Copilot Studio each call costs Copilot credits unless the user has a Finance Premium or Supply Chain Management Premium license. Use Microsoft's server on the environments it supports when users need forms or X++ actions and this one where that server is not available, such as the LCS VHD one-box or a cloud-hosted dev box, or when you want a small server you can read and change.

## Tools

| Tool | What it does |
| --- | --- |
| `environment_info` | Checks the connection and returns the application version, the legal entities, the configured company and whether writes are on |
| `search_entities` | Finds data entities by name and returns the OData collection name, with `total`, `returned` and `hasMore`. Without a match it suggests close names |
| `describe_entity` | Lists the fields of an entity with type, key, mandatory and label, plus the enum type and its element names for enum fields |
| `query_entity` | Reads records with `$filter`, `$select`, `$orderby`, `$expand`, `$top`, `$skip` and `$count`, scoped to a company or across companies |
| `create_record` | Creates a record and returns its key, the data sent and the created record. Only when `FO_ALLOW_WRITES=1` |
| `update_record` | Reads a record, updates the given fields and returns them before and after. Only when `FO_ALLOW_WRITES=1` |

The server is read-only by default. `FO_ENTITIES` limits the tools to a list of collections, for example `CustomersV3,SalesOrderHeadersV2`, which is narrower than the F&O role of the mapped or signed in user. With the list set, `expand` only reaches related entities that are on it. `filter`, `orderby` and `select` cannot follow navigation properties and `select` takes no options in parentheses such as `SalesOrderLines($select=ItemNumber)`, those belong in `expand`. Whatever the list says, `environment_info` reads the IDs and names of the legal entities from `LegalEntities` and the versions from two actions on `DataManagementEntities` and `DocumentRoutingClientApps`. `query_entity` reads `LegalEntities` too when a company returns no rows, to say whether that company exists. `environment_info` reports names on `FO_ENTITIES` or `FO_WRITE_ENTITIES` that match no OData collection under `problems`, for example a public entity name such as `CustomerV3` where the collection name `CustomersV3` belongs. The `FO_WRITE_ENTITIES` check runs whenever `FO_ALLOW_WRITES` is on, also from a session without the write tools. `writeEntities` is listed in the answer then too. With `FO_ALLOW_WRITES=0` the list is neither checked nor shown.

### Reading

- **Strict arguments.** Every tool except `environment_info` refuses an argument it does not know and names the valid ones. A `$filter` or `orderBy` passed by mistake fails instead of returning every row unfiltered. Arguments have length limits far above what F&O takes: 128 characters for an entity, a company or a field name in `data`, `key` and `expected`, 1,000 for the search query and `fields`, 8,000 for `filter`, `select`, `orderby` and `expand`. An error or hint about names that match no field lists at most 20 of them and suggests close names for the first 5, since each suggestion compares a name with every field of the entity. The remote server accepts at most 100 KB in one request and answers a larger one with 413 and a message that names the limit.
- **Filters.** F&O supports only `eq` and `ne` on string fields. A partial match is a `*` wildcard inside `eq`, for example `Name eq '*contoso*'`. Matching is case insensitive. The tool descriptions tell Claude this up front, together with the forms of enum and date literals. The server puts the filter in parentheses next to the company clause, so a filter whose parentheses do not pair up or whose string literal is never closed is refused before anything is sent.
- **Legal entities.** `query_entity` reads the default company `FO_COMPANY` unless `company` names one legal entity or `crossCompany` reads all of them. `company` takes one legal entity ID, a value with `*` or `?` is refused by all three tools that take it, since F&O reads them as wildcards. A read across legal entities, with `crossCompany`, without a default company or with `dataAreaId` in `filter`, adds `dataAreaId` to a plain `select` that lacks it, since master data repeats the same IDs in every company.
- **Searching.** `search_entities` returns `total` (every match), `returned` (the matches in this answer, at most `top`) and `hasMore`. When more match than are shown, a hint asks for more words in the query.
- **Fields.** `describe_entity` takes `fields` as parts of field names separated by commas or spaces, for example `credit` or `CustomerAccount,CreditLimit`. It keeps every field whose name contains one of them, in any letter case. A part that matches no field comes back in a hint with the closest field names, for example `OrgName` with `OrganizationName`, so an empty list is never the only answer. A wrong `expand` name gets F&O's own error for an unknown property plus a pointer to `includeNavigation`, since the field list of `describe_entity` does not show navigation properties.
- **Paging.** `query_entity` returns 20 rows unless `top` asks for more, at most 500. Every answer has `returned` (the rows in this answer) and `hasMore`. While more rows may follow, `nextSkip` is the `skip` of the next call. Without `count=true` a full page is the only sign of more rows, so `hasMore` can be true when the next page is empty. When more rows follow and no `orderby` is given, a hint asks for `orderby` on the key fields, because F&O promises no stable order between pages. `count=true` adds `totalCount`. A pure count, with `top=1` or a page of at most one row as F&O sent it, gets no paging hint, since the count is what was asked for. A page cut to its first row by the size limit keeps the hint, since its `nextSkip` invites the next page. A count with a page of rows gets a hint that `totalCount` is the total and that the pages need `orderby` on the key fields.
- **Result size.** Tool results are capped at 40 KB, the echoed request and the hints included, which stays well inside what Claude Code accepts from one tool call. `query_entity` keeps whole rows until the next one would not fit, then marks the answer `truncated` with `fetched`, the rows F&O sent. Pass `select` to get more rows per call. A single row over that limit is refused with the names and sizes of its largest fields, or with advice to drop `expand` when one was passed. A row that fits the limit but not next to a long echoed request is refused with advice to shorten the request. `describe_entity` first leaves out labels and enum values, then cuts the field list with a hint to narrow it with `fields`. When an estimate of the answer says that labels and enum values would not fit, it leaves them out from the start, also when `fields` still matches most of a wide entity. One label request per field would cost seconds for text that is dropped anyway.
- **Memory.** F&O answers over 4 MB from `/data` or 20 MB from `/Metadata` are refused with a hint to narrow the query. All tool calls together hold at most 96 MB of F&O answers. Past that a read fails with a message that the server is busy, which asks Claude to try again in a moment or to pass `select`.
- **Enums.** For every enum field `describe_entity` returns `enumType`, the qualified name that filters need, plus `values` with the plain element names that `data`, `key` and `expected` take. A key value in the qualified form is cut to its element name. On a NoYes key `true` and `false` stand for Yes and No, any other enum key refuses them. An enum with more than 30 elements gets `valueCount` instead of `values`. A call with `fields` naming that field lists every element. F&O's error for a wrong element name points there.
- **Load.** At most 6 tool calls of one F&O user run at once and 48 on the whole server. Claude Code sends calls of read-only tools in parallel, often more than six, so a call past the 6 of its user waits for one of them to end, within its own time budget. Up to 10 calls of one user wait, in order of arrival. Only a user with 6 calls running has a queue, so at most 80 calls wait on the whole server. An 11th waiting call, or one that would be the 49th to run, fails at once with a message to wait. A call that finds no place within its time budget fails with a message to make fewer calls at once. A read that F&O throttles with a `Retry-After` is repeated once when the wait fits in the time budget of the call.

### Writing

With `FO_ALLOW_WRITES=1`:

- `create_record` and `update_record` take an optional `company` for company specific entities. It sets `dataAreaId` and defaults to `FO_COMPANY`. Without a default company it is required. The descriptions of both tools name the environment, the default company and, with `FO_WRITE_ENTITIES` set, the entities that may be written. They ask Claude to state the environment, the legal entity, the entity, the key and the values and to get the user's confirmation before it writes.
- Field names in `data`, `key` and `expected` are checked against the entity before anything is sent. A misspelled name comes back with the closest field names. Navigation properties and annotations are refused, a related entity is written with its own call.
- `create_record` returns the `key` of the new record and the `data` it sent. The key includes values F&O took from a number sequence. Up to 8 KB the answer also holds `created`, the record as F&O stored it. A bigger record gets a note to read the fields it needs with `query_entity` and `select`. When F&O accepts the create without sending the record back, the answer says so and asks Claude to read it before doing anything else.
- `update_record` addresses the record by `key` and the legal entity. `company`, `dataAreaId` in `key` and `dataAreaId` in `data` must name the same legal entity, any disagreement is refused. `dataAreaId` in `data` only selects the record and is not sent as a change. A key field in `data` with the value of the key is dropped. One with another value is refused, because an update cannot change a key. `data` that only repeats the key is refused as nothing to update.
- `update_record` reads the record before it writes. A key that matches no record stops the update with nothing sent. The same happens when a value in the optional `expected` argument, the value the user saw, no longer matches. Values are compared the way F&O compares them. Numbers compare as numbers, enums by element name (`true` and `false` stand for Yes and No), dates by their date part, timestamps by the instant and text without regard to letter case. X++ has no null and stores no value as empty text, 0 or 1900-01-01, so `null` matches those for text, number and date fields. A key that F&O cannot address by its URL, which can happen when it holds `&`, `:` or `+`, stops the update too, with an error that says so. `query_entity` finds such a record with `$filter`, but it has to be changed in F&O itself. A slash or backslash in a text key is refused before anything is sent, for the same reason. After the PATCH it reads the record again and returns `before` and `after` of the changed fields, with a warning when F&O stored other values than requested. The read and the PATCH are separate requests, so a change made between them is not caught.
- `FO_WRITE_ENTITIES` limits which collections may be written, for example `CustomerGroups`. With `FO_ENTITIES` set every write entity must be on that list too. Without `FO_WRITE_ENTITIES` the server may write every entity it reads and warns about that at start.
- A create or update is never repeated after throttling, only a read is. It is not sent at all when less than 5 seconds of the time budget of the call are left (half the budget when `FO_TIMEOUT_MS` is under 10 seconds). That error says that nothing changed. Once it went out, a timeout, a cancel, a broken connection or a gateway answer of 502, 503 or 504 leaves the outcome open. So does a restart of either server when F&O does not answer within the time a sent write gets after SIGTERM, 20 seconds on the remote server and 1.5 seconds on the local one. The error then says that F&O may still have created the record, so check with `query_entity` before repeating a create, or that it may still have applied the update, so read the record before trying again.

## Setup

Requires Node 22.19 or newer. Tested on Node 24 with F&O 10.0.48.

1. Register an application in Microsoft Entra ID: single tenant, no redirect URI, no API permissions. Copy the **Application (client) ID** and the **Directory (tenant) ID**, then create a client secret under **Certificates & secrets** and copy its value right away.
2. In F&O go to **System administration > Setup > Microsoft Entra ID applications** and add the client ID mapped to a user. Everything the server does runs as that user, see Service user below.
3. Clone and build. `npm ci` installs the exact versions from `package-lock.json` and `npm run build` compiles `dist`:

```bash
git clone https://github.com/pericluka/d365fo-mcp.git
cd d365fo-mcp
npm ci
npm run build
```

In a shell where `NODE_ENV=production` is set, `npm ci` leaves out the TypeScript compiler. Use `npm ci --include=dev` there, or build elsewhere and copy `dist`.

4. Copy `.env.example` to `.env` and fill in `FO_URL`, `FO_TENANT_ID`, `FO_CLIENT_ID`, `FO_CLIENT_SECRET` and `FO_COMPANY`.
5. Check that it works:

```bash
node scripts/call.mjs environment_info
node scripts/call.mjs query_entity '{"entity":"CustomersV3","select":"CustomerAccount,OrganizationName","top":5}'
```

`node scripts/call.mjs` without arguments lists the tools with their arguments. The first call after the environment starts may come back with a No answer message while F&O builds its metadata, because the server gives up after 50 seconds instead of hanging. Run it again and the second call answers in about a second.

### Service user

- Create a dedicated user for the server and give it a security role with only the privileges you need. Do not map the app to Admin on a shared environment and never turn writes on with an Admin mapping there. The author's own box uses Admin because it is a throwaway one-box VM.
- No Entra API permissions or admin consent are needed. The server asks for a token with the `<FO_URL>/.default` scope and F&O authorises the client ID through the mapping above.
- `FO_COMPANY` is the default legal entity for company specific entities. Reads use it unless Claude passes `company` or `crossCompany`, writes unless Claude passes `company`. It is a default and not a security boundary. Only the F&O roles of the user decide which legal entities the server can reach. Leave it empty to read all companies, writes then need `company`.
- `FO_NAME` names the environment for Claude, for example PROD or TEST. Default is the host of `FO_URL`. The instructions and the write tool descriptions carry it. Before a write Claude states the environment, the legal entity, the entity, the key and the values and asks for confirmation, so two connectors in one chat can be told apart. On the remote server a name set here also appears as the resource name in the metadata that answers anyone, so do not put anything confidential in it. Without it that metadata names no environment.
- Users who sign in through the remote server are named F&O users with the licenses their roles need. Several people working through the one mapped service user of the local server is the multiplexing case of the Dynamics 365 licensing guide, check it with your licensing partner.
- Every row a tool returns becomes part of the conversation at your model provider. When that matters, keep entities with a lot of personal data, such as workers and contacts, off the `FO_ENTITIES` list.

## Claude Code

```bash
claude mcp add fo-mcp --scope user -- "$(which node)" /absolute/path/to/d365fo-mcp/dist/index.js
```

The server reads `.env` from its own folder, so no environment variables are needed in the Claude configuration. It runs from the clone, it is not published to npm and does not run through `npx`. On Windows write the full path to `node.exe` instead of `$(which node)`.

## Claude Desktop

Add to `claude_desktop_config.json`:

```json
{
  "mcpServers": {
    "fo-mcp": {
      "command": "/absolute/path/to/node",
      "args": ["/absolute/path/to/d365fo-mcp/dist/index.js"]
    }
  }
}
```

Claude Desktop does not read your shell PATH, so a `node` installed with nvm, fnm, volta or Homebrew is not found when `command` is just `node`. Use the full path that `which node` prints.

When the client stops the local server, the server handles SIGTERM and SIGINT the way the remote server does, see Hosting on Azure. The tool calls in flight answer at once that the server is restarting, a create or update already sent gets up to 1.5 seconds for F&O's answer and each of them still writes its audit line, then the process exits. The grace is that short because an MCP client built on the MCP SDK, Claude Code among them, ends stdin when it is done, sends SIGTERM two seconds later when the process still runs and SIGKILL two seconds after that. A write that F&O has not answered within the grace is answered with its outcome left open, as after a timeout. Its audit line says so.

## Windows

Write paths in `claude_desktop_config.json` with doubled backslashes. In `.env` write them unquoted, in single quotes or with forward slashes (`C:/Users/...`), never in double quotes. Inside double quotes `\n` becomes a newline and Explorer's Copy as path adds double quotes. Run the `scripts/call.mjs` examples in PowerShell 7.3 or newer, where the single quoted JSON argument works as written. Windows PowerShell 5.1 drops the quotes inside it. In cmd.exe put the JSON in double quotes and escape the quotes inside it with backslashes, `node scripts/call.mjs query_entity "{\"entity\":\"CustomersV3\",\"top\":5}"`. The bash form `MCP_PORT=3456 node dist/http.js` under Remote server is `$env:MCP_PORT=3456; node dist/http.js` in PowerShell, or put `MCP_PORT=3456` in `.env` and run `node dist/http.js` in any shell. For `npm test` on Windows see Tests and evals.

## LCS VHD one-box

The downloadable VHD uses a self-signed certificate and a host name that only resolves inside the VM. To use it from another machine:

- open port 443 for your IP address in the network security group of the VM,
- set `FO_HOST_IP=<vm public ip>` in `.env` so the server resolves the F&O host name itself (only the F&O host is affected, the token request to Entra uses normal DNS; if your shell sets `HTTPS_PROXY` the F&O host bypasses the proxy because a proxy cannot resolve the one-box name),
- export the one-box certificate inside the VM and point `FO_CA_FILE` at it: open the F&O site in the browser there, view the certificate, export it as Base64 encoded X.509 (.CER), which is the same PEM format, copy the file out and set `FO_CA_FILE=onebox.pem`. The certificate is self-signed, so a copy fetched over the internet, for example with `openssl s_client -connect <vm public ip>:443 -servername usnconeboxax1aos.cloud.onebox.dynamics.com -showcerts </dev/null | openssl x509 > onebox.pem`, is only as good as that one connection. Before you trust such a copy, compare `openssl x509 -in onebox.pem -noout -fingerprint -sha256` with the SHA-256 fingerprint the browser inside the VM shows (or `-sha1` with the thumbprint of the Windows certificate dialog),
- or, as a last resort, set `FO_INSECURE_TLS=1` to skip certificate checks for the F&O host. The remote server accepts it only while `MCP_PUBLIC_URL` is on localhost, unless `FO_CA_FILE` is set too, then `FO_CA_FILE` wins and the flag has no effect.

## Remote server

`node dist/http.js` serves the tools over Streamable HTTP at `/mcp`. Claude discovers that the server wants a sign in and opens the server's sign in page in the browser. From then on every tool call carries the user's identity: the server exchanges the user's token for an F&O token of the same user with the on-behalf-of flow. F&O applies that user's security roles, entity privileges and extensible data security (XDS) policies. OData runs the entity and table logic, not the logic of forms, so a change through the server can behave differently from the same change made in a form. Entra tokens never reach Claude and the tokens Claude holds never reach F&O.

### Sign in

1. The client registers at `/register`. Nothing is stored: the client ID the server returns carries the client's name and redirect URIs and is signed by the server.
2. The client opens `/authorize` in the browser. The first time a browser sees a client, the server shows a consent page with the name the client gave itself, the address the result goes to and what the client gets. Approve is remembered in that browser for 30 days, for up to 20 clients. It holds only while the server stays as it was approved: turning writes on or off, another `MCP_WRITE_ROLE` while writes are on or another F&O host in `FO_URL` shows the page again. A remembered client skips the page. The server then sends `prompt=select_account` to Entra, so Microsoft asks the user to pick the account instead of signing in silently. A sign in the user did not start is then still visible and can be closed. To make a browser forget every approval, open `/forget` on the server in that browser. The consent page links to it. Cancel sends the client back `access_denied`. The page is valid for 10 minutes.
3. The browser goes on to the Entra sign in and comes back to `/callback`, again within 10 minutes. The Entra sign in is silent when the user is signed in already and just approved the client on the consent page. For a remembered client Microsoft shows the account picker. A cookie binds the sign in to the browser that started it, so the callback works only there and only once.
4. The client trades the code for the server's own access and refresh tokens at `/token`. `/revoke` ends a sign in.

A sign in in progress is stored nowhere on the server. `/authorize` seals the request into the consent form. On the way to Entra the server seals it again into the state it sends there, together with its own PKCE verifier and a hash of the browser's cookie. Sealing is AES-256-GCM with a key derived from the signing key below, so the browser carries the sign in but can neither read nor change it. A flood of `/authorize` requests therefore costs no memory. A sign in started before a restart also finishes after it. The server only remembers the states of callbacks that Entra answered with a working code, until they expire, to refuse them a second time.

The consent page accepts an approval only from itself. The form post must carry an `Origin` equal to the origin of `MCP_PUBLIC_URL`, or, when the browser sends no `Origin` or `null`, `Sec-Fetch-Site: same-origin`. Anything else gets a 403 page. On https the cookies are called `__Host-fo_consent`, `__Host-fo_csrf` and `__Host-fo_signin_<id>`, which browsers accept only from the server's own host, with `Path=/`, `Secure` and no `Domain`, so no other host can plant one. A cookie name that arrives twice counts as missing. On `http://localhost` the same cookies go without the `__Host-` prefix, which needs https.

Client IDs, remembered approvals and the consent form are signed with `MCP_STATE_KEY`, or with a key derived from `FO_CLIENT_SECRET` when it is not set. Sign ins in progress are sealed with a key derived from that signing key. Registrations therefore survive a restart and work on every replica with the same key. Changing `MCP_STATE_KEY`, or rotating the client secret while it is not set, makes every registration, approval and sign in in progress invalid. `/token` then answers `invalid_client`, which makes clients built on the MCP SDK register again on their own. `/authorize` shows a page that asks the user to remove the connector and add it again.

### Entra setup

On a personal box the app registration from Setup can serve both modes, the author's own box works that way. For a shared or production environment register a second app for the hosted server and do not add it under **Microsoft Entra ID applications** in F&O. The on-behalf-of flow needs no mapping. A mapped app's secret lets whoever holds it act as the mapped user with nobody signed in. Register one app per hosted server. With one app for a TEST and a PROD server the app roles are shared as well, so a tester with `FO.Write` for TEST has the write tools on PROD too, the role comes with every token of that app. Where the servers must share an app, give each its own role value, for example `FO.Write.Test` and `FO.Write.Prod`, with the matching `MCP_WRITE_ROLE` on each server.

On the server's app registration:

1. **Expose an API**: set the Application ID URI to `api://<client id>` and add a scope named `access_as_user` (admins and users can consent). This is the scope users sign in with. Under **Authorized client applications** add the app's own client ID with that scope, so the sign in asks nobody to consent to it.
2. **Authentication**: add a Web redirect URI for the server's callback, `<origin of MCP_PUBLIC_URL>/callback`, for example `http://localhost:3456/callback` while testing and `https://<your host>/callback` once hosted. Remove the localhost callback from the app of a production server. Claude's own redirect URIs are handled by the server, Entra never sees them. Leave **Allow public client flows** off on this app.
3. **API permissions**: add **Dynamics ERP** (Microsoft APIs, under More Microsoft APIs) with the delegated permissions `AX.FullAccess` and `Odata.FullAccess`, plus **Microsoft Graph** with the delegated permissions `openid`, `profile` and `offline_access`, which the sign in asks for. Then **Grant admin consent**, which covers everything on the list. Without the Graph permissions here and the authorized client of step 1, a tenant that restricts user consent, the setting Microsoft recommends among them, stops the first sign in of every user at **Need admin approval**, since the scope of a custom API never counts as a low impact permission. The LCS VHD one-box needs nothing extra, Entra maps the one-box URL to the same Dynamics ERP app. If the consent fails because the organization *does not have a subscription (or service principal)* for Dynamics ERP (AADSTS650052 on the consent page), the tenant has never used it. Create its service principal once with `az ad sp create --id 00000015-0000-0000-c000-000000000000` and grant the consent again.
4. Only with `MCP_WRITE_ROLE`: under **App roles** create a role with the allowed member types Users/Groups and a value such as `FO.Write`. Then in **Enterprise applications** open the app, go to **Users and groups** and add the users or a group with that role (assigning a group needs Entra ID P1 or P2). Set `MCP_WRITE_ROLE=FO.Write`.
5. **Conditional Access**: add the server's app to every policy that covers Dynamics 365, with the same controls, MFA, a compliant or hybrid joined device or a sign in frequency. Entra applies those policies when the server trades the user's token for an F&O token, not only at the sign in. A user whose sign in to the server's app did not satisfy them gets no F&O token. Entra answers the on-behalf-of request with `AADSTS50076` (MFA) or `AADSTS53000` (device) and `interaction_required`, so every tool call fails with a token request error that names the code. The server passes no claims challenge on, so the hint in that error to sign in again helps only once the policy covers the server's app. Until then the sign in to the app succeeds and nothing asks for the second factor. Block the device code flow for the app with the **Authentication flows** condition while you are there.

`scripts/login-test.mjs` signs in with the device code flow, which needs public client flows. Register a separate single tenant test app for it with **Allow public client flows** on. Under **API permissions** > **My APIs** add the `access_as_user` permission of the server's app and grant consent. Put its client ID in `LOGIN_TEST_CLIENT_ID` and in `MCP_ALLOWED_CLIENT_APPS` of the server. Without `LOGIN_TEST_CLIENT_ID` the script signs in as `FO_CLIENT_ID`, which needs public client flows on the server's own app and works only against a server on localhost, or one that lists `FO_CLIENT_ID` in `MCP_ALLOWED_CLIENT_APPS`. Keep that to a personal test box. Some tenants block the device code flow and refuse access right after the password, `scripts/oauth-test.mjs` signs in through the browser instead.

In F&O every user who signs in needs a user record with their Entra email and the roles they should get. The mapping under Microsoft Entra ID applications is what authorises the client credentials of the local mode, delegated tokens are authorised by the user. A user without an F&O user record gets 403 with *Please verify that the user is valid and set up correctly*, even when the app itself is mapped to Admin. A user with a narrow role gets *User is not authorized to read view* for everything outside that role. A personal Microsoft account that is a member of the tenant (outlook.com, gmail.com and so on) needs the provider `live.com` instead of `https://sts.windows.net/`, with the account's email as the email.

### Run it

Fill in the `MCP_` variables of `.env.example` or set them as environment variables. For a local test leave `MCP_PUBLIC_URL` empty, it then follows `MCP_PORT`. Then:

```bash
MCP_PORT=3456 node dist/http.js
node scripts/oauth-test.mjs http://localhost:3456/mcp          # consent page and browser sign in, then calls environment_info
node scripts/login-test.mjs http://localhost:3456/mcp          # device code sign in with the test app, token straight from Entra
```

On Windows see Windows for the PowerShell form of the first line. `environment_info` reports the signed in user, `query_entity` returns what that user may see. `/health` answers `{"status":"ok","name":"fo-mcp","version":"..."}` and nothing about the environment or its users. It answers for any `Host` header, so a liveness or readiness probe on the replica's own address works. Every other path answers only for the host of `MCP_PUBLIC_URL` and the names on `MCP_ALLOWED_HOSTS`.

| Variable | Default | What it does |
| --- | --- | --- |
| `MCP_PORT` | `3000` | Port to listen on, 1 to 65535 |
| `MCP_HOST` | `127.0.0.1` when `MCP_PUBLIC_URL` is on localhost or 127.0.0.1, else `0.0.0.0` | Address to listen on. The Docker image sets `0.0.0.0` |
| `MCP_PUBLIC_URL` | `http://localhost:<MCP_PORT>/mcp` | The URL Claude connects to. Plain http only on localhost or 127.0.0.1. Required when `MCP_HOST` is not a loopback address |
| `MCP_AUDIENCE` | `api://<FO_CLIENT_ID>` | Audience of the user tokens |
| `MCP_SCOPE` | `<MCP_AUDIENCE>/access_as_user` | Scope users sign in with |
| `MCP_ALLOWED_HOSTS` | the host of `MCP_PUBLIC_URL` | Extra host names the server answers for, such as the generated `azurecontainerapps.io` name when a proxy in front keeps it as the `Host` header, see Hardening |
| `MCP_ALLOWED_CLIENT_APPS` | `FO_CLIENT_ID` when `MCP_PUBLIC_URL` is on localhost or 127.0.0.1, else none | App IDs whose own Entra tokens `/mcp` accepts, see Remote server notes. `none` turns them off |
| `MCP_TRUST_PROXY` | `1` | Proxies in front of the server that append to `X-Forwarded-For`, 0 to 10. The limits per address take the client address that many entries from the end, see Security notes. `0` uses the address of the connection |
| `MCP_WRITE_ROLE` | empty | App role a user needs for `create_record` and `update_record`. Empty gives them to every signed in user while `FO_ALLOW_WRITES=1` |
| `MCP_STATE_KEY` | derived from `FO_CLIENT_SECRET` | At least 32 characters, for example from `openssl rand -base64 32`. The same value on every replica. Set it before the first user signs in, so a rotation of `FO_CLIENT_SECRET` does not end every registration and approval |

With `MCP_WRITE_ROLE` set, a session offers the write tools only when the user's token carries that value in its `roles` claim, matched case sensitively. The tools of a session are fixed when it starts. A role that is assigned or removed reaches the server with the user's next Entra token, at the next sign in or token refresh, which comes about once an hour. The server then ends each session of that user whose tools no longer match, at its next request, so that the client starts a new session with or without the write tools. A client that does not start one on its own needs the connector reconnected. Until the role arrives, `environment_info` in a session without the write tools says which role they need. A session that ends while one of its tool calls still runs, because the user's write role changed, because the user's or the server's session limit evicted it or because it was idle for an hour, takes no further request at once but is closed only after those calls have answered. A create or update already sent to F&O therefore still gets its answer, like it does on SIGTERM. A DELETE from the client ends the session at once.

The server refuses to start when `MCP_PUBLIC_URL` uses http on a host other than localhost or 127.0.0.1, when `MCP_PUBLIC_URL` is empty while `MCP_HOST` is an address other than localhost, 127.0.0.1 or ::1, when `MCP_PORT` is not a whole number from 1 to 65535, when `FO_INSECURE_TLS=1` is set without `FO_CA_FILE` and the public URL is not on localhost, when `NODE_TLS_REJECT_UNAUTHORIZED=0` is set and the public URL is not on localhost, when `FO_TENANT_ID` is not a GUID, when `MCP_ALLOWED_CLIENT_APPS` holds something other than GUIDs or `none`, when `MCP_TRUST_PROXY` is not a whole number from 0 to 10 and when `MCP_STATE_KEY` is shorter than 32 characters. Plain http on `[::1]` is refused too, because the MCP SDK does not accept an http issuer there, so use `http://127.0.0.1` instead. It also stops when Entra answers the metadata request for the tenant with an error or a redirect. On localhost `NODE_TLS_REJECT_UNAUTHORIZED=0` only gives a warning at start, as it does for the local server. It starts with a warning when `MCP_HOST` listens beyond this machine while `MCP_PUBLIC_URL` is on localhost, when `MCP_WRITE_ROLE` is set with writes off and, off localhost, when `MCP_ALLOWED_CLIENT_APPS` lists `FO_CLIENT_ID` or writes are on without `MCP_WRITE_ROLE`.

Connect Claude:

- **claude.ai and Claude Desktop**: Settings > Connectors > Add custom connector, URL `https://<your host>/mcp`. The consent page and the sign in open in the browser.
- **Claude Code**: `claude mcp add --transport http fo-mcp https://<your host>/mcp`, then `/mcp` to sign in.

### Hosting on Azure

The `Dockerfile` builds the server image. Azure Container Apps gives it HTTPS, a public name and secrets. The smallest replica (0.25 vCPU, 0.5 GiB) kept on all month costs roughly 15 dollars after the free grant when it is busy all the time. A replica that mostly waits is billed at the lower idle rate, which comes to about 5 dollars. `az containerapp up --source .` below also creates an Azure Container Registry to build the image in. In the Basic tier it costs about 5 dollars a month whether it is used or not. The app pulls its image from it whenever a replica starts, so it stays as long as the app does. Add `--registry-server <name>.azurecr.io` to build in a registry you already have instead. The commands below use the generated `azurecontainerapps.io` name. Move the server to a custom domain once it runs, see Hardening:

```bash
az group create -n fo-mcp -l swedencentral
az containerapp env create -n fo-mcp-env -g fo-mcp -l swedencentral
FQDN=fo-mcp.$(az containerapp env show -n fo-mcp-env -g fo-mcp --query properties.defaultDomain -o tsv)
az containerapp up -n fo-mcp -g fo-mcp --environment fo-mcp-env --source . \
  --ingress external --target-port 3000 \
  --env-vars FO_URL=https://your-environment.operations.dynamics.com FO_TENANT_ID=<tenant> FO_CLIENT_ID=<client id> FO_COMPANY=USMF MCP_PUBLIC_URL=https://$FQDN/mcp
```

Keep the client secret in a Key Vault with the Azure role-based access control permission model. Add it in the portal under **Secrets**, so it never passes through a shell. Put `MCP_STATE_KEY` next to it before the first user connects, generated straight into the vault. Without it the key that signs registrations and remembered approvals is derived from the client secret, so the first rotation of that secret unregisters every connector and asks every browser for its approval again, see Security notes. Then let the app read both with its managed identity:

```bash
az keyvault secret set --vault-name <vault> --name mcp-state-key --value "$(openssl rand -base64 32)"
PRINCIPAL=$(az containerapp identity assign -n fo-mcp -g fo-mcp --system-assigned --query principalId -o tsv)
az role assignment create --assignee-object-id $PRINCIPAL --assignee-principal-type ServicePrincipal \
  --role "Key Vault Secrets User" --scope $(az keyvault show -n <vault> --query id -o tsv)
az containerapp secret set -n fo-mcp -g fo-mcp \
  --secrets fo-client-secret=keyvaultref:https://<vault>.vault.azure.net/secrets/fo-client-secret,identityref:system \
            mcp-state-key=keyvaultref:https://<vault>.vault.azure.net/secrets/mcp-state-key,identityref:system
az containerapp update -n fo-mcp -g fo-mcp --cpu 0.25 --memory 0.5Gi --min-replicas 1 --max-replicas 1 \
  --set-env-vars FO_CLIENT_SECRET=secretref:fo-client-secret MCP_STATE_KEY=secretref:mcp-state-key
```

The first revision stops right after the start because `FO_CLIENT_SECRET` is not there yet, the update fixes that. Then add `https://$FQDN/callback` as a redirect URI in Entra. A new role assignment can take a few minutes to apply, so run the last two commands again when the secrets cannot be read yet. Never put the client secret on a command line, it stays in the shell history. The managed identity only reads the secrets, the server still signs in to Entra with `FO_CLIENT_SECRET`.

The audit lines and the request log, which the server writes to stderr, go to the Log Analytics workspace of the environment. `az containerapp env create` without `--logs-destination` creates one with a generated name in the resource group. `az containerapp logs show -n fo-mcp -g fo-mcp --follow` shows the live stream of the replica, the history is in the `ContainerAppConsoleLogs_CL` table of the workspace, one row per line in `Log_s`. That table is the audit trail of the server and it holds personal data, the user, the Entra object ID and the keys of written records, with `FO_AUDIT_VALUES=1` the written values too, see Security notes. Everyone with the Log Analytics Reader role on the workspace, the resource group or the subscription reads it, so limit that like access to F&O data. A workspace keeps its rows for 30 days unless its retention is set to the time the company needs, with `az monitor log-analytics workspace update -g fo-mcp -n <workspace> --retention-time <days>`.

Keep one replica. Codes, tokens and MCP sessions live in memory, so a second instance does not know them and a restart means signing in again. Registrations, remembered approvals and sign ins in progress survive because they are signed or sealed, not stored.

Memory decides how many people one replica serves. All tool calls together hold at most 96 MB of F&O answers, but parsing and trimming them takes several times that. Against the fake F&O of the tests, 48 tool calls at once that each read 3.5 MB of wide rows without `select` took the process to between 400 and 550 MB, 6 such calls of one user to about 320 MB. 0.5 GiB is enough for a few people. When more use the server at the same time, give the replica 1 GiB, which on Container Apps comes with 0.5 vCPU (`--cpu 0.5 --memory 1Gi`). A replica that runs out of memory restarts and every user has to sign in again.

On SIGTERM, which Container Apps sends before it stops a replica, the server takes no new connections and stops the tool calls in flight. They answer at once that the server is restarting. A create or update that already went out gets up to 20 seconds more for F&O's answer, so the user learns whether it was applied. Past that it answers with the note that F&O may have applied it. Each of them still writes its audit line. The process exits once those answers are out, or after 25 seconds while a sign in still waits for Entra.

The server keeps an idle connection open for 65 seconds instead of Node's 5 second default, with a headers timeout of 70 seconds. The Container Apps ingress pools its connections to the replica and does not read the `Keep-Alive` header, so with the default it could send the next tool call onto a connection the server was closing at that moment, which showed up as an occasional reset. The value is fixed.

On an Azure free trial ACR Tasks are not allowed and `--source` fails with `TasksOperationsNotAllowed`. Build the image yourself and push it to a registry instead, then pass `--image` in place of `--source .`. Container Apps runs only linux/amd64 images, so pin the platform when you build on an ARM machine such as an Apple Silicon Mac:

```bash
az acr create -n <registry> -g fo-mcp --sku Basic --admin-enabled true
az acr login -n <registry>
docker build --platform linux/amd64 -t <registry>.azurecr.io/fo-mcp:1 . && docker push <registry>.azurecr.io/fo-mcp:1
```

Then run `az containerapp up` with `--image <registry>.azurecr.io/fo-mcp:1 --registry-server <registry>.azurecr.io` and without `--registry-username` and `--registry-password`. The CLI reads the admin credentials of the registry itself and stores the password as a secret of the app, so it never passes through the shell history. A registry password there is as bad as the client secret, whoever reads it pushes an image of their own and the next replica starts from it with `FO_CLIENT_SECRET` and every user's token. Once the app has its managed identity from the Key Vault step above, let it pull with that and turn the admin user off:

```bash
az role assignment create --assignee-object-id $PRINCIPAL --assignee-principal-type ServicePrincipal \
  --role AcrPull --scope $(az acr show -n <registry> --query id -o tsv)
az containerapp registry set -n fo-mcp -g fo-mcp --server <registry>.azurecr.io --identity system
az acr update -n <registry> --admin-enabled false
```

A registry outside Azure needs its credentials passed, so read them into `--registry-password` from an environment variable or a file instead of typing them.

The image listens on every interface inside the container, so it refuses to start without `MCP_PUBLIC_URL`. For a local `docker run` pass `-e MCP_PUBLIC_URL=http://localhost:3000/mcp` and publish the port on the loopback address only, `-p 127.0.0.1:3000:3000`. The server then warns at start that it listens beyond localhost with the localhost defaults. Publishing the port on the loopback address is what keeps them on your machine.

For the LCS one-box behind a network security group, allow the outbound IP of the container app on port 443 (`az containerapp show -n fo-mcp -g fo-mcp --query properties.outboundIpAddresses`), set `FO_HOST_IP` and give the server the certificate as a secret mounted as a file:

```bash
az containerapp secret set -n fo-mcp -g fo-mcp --secrets onebox-pem="$(cat onebox.pem)"
az containerapp update -n fo-mcp -g fo-mcp --secret-volume-mount /mnt/secrets \
  --set-env-vars FO_HOST_IP=<vm public ip> FO_CA_FILE=/mnt/secrets/onebox-pem
```

### Hardening a hosted server

- **Custom domain.** Use a name of your own such as `mcp.example.com` instead of the generated `azurecontainerapps.io` one. That domain is not on the Public Suffix List, so for a browser every Container App on it, of any Azure customer, is the same site as your server. Pages of those apps can set cookies for the whole domain and post forms to your server with its `SameSite=Lax` cookies attached. The server guards against that with `__Host-` cookies, by ignoring a cookie name that arrives twice and by accepting an approval only from its own consent page, see Sign in. A domain of your own takes the server out of that shared site altogether. Create a CNAME record from the name to `$FQDN` and a TXT record `asuid.mcp.example.com` with the value of `az containerapp show -n fo-mcp -g fo-mcp --query properties.customDomainVerificationId -o tsv`. Then add the name with `az containerapp hostname add -n fo-mcp -g fo-mcp --hostname mcp.example.com` and bind a free managed certificate with `az containerapp hostname bind -n fo-mcp -g fo-mcp --environment fo-mcp-env --hostname mcp.example.com --validation-method CNAME`. Set `MCP_PUBLIC_URL=https://mcp.example.com/mcp`, add `https://mcp.example.com/callback` as a redirect URI in Entra and remove the one on the generated name. The issuer changes with the URL, so connectors added before have to be removed and added again.
- **Assignment required.** In **Enterprise applications** open the server's app, set **Assignment required** to Yes under **Properties** and assign a group of F&O users under **Users and groups**. Everybody else is stopped at the Entra sign in.
- **Conditional Access.** The policies that cover Dynamics 365 must cover the server's app, otherwise the on-behalf-of exchange fails for every user they apply to, see Entra setup. Block the device code flow for the app with the **Authentication flows** condition.
- **`MCP_STATE_KEY` before the first sign in**, from Key Vault as above. Without it a rotation of `FO_CLIENT_SECRET` unregisters every connector and every browser has to approve the consent page again, on the same morning.
- **Logs in a workspace of your own.** The audit lines land in the Log Analytics workspace of the environment, see above. Create the environment with `--logs-destination log-analytics --logs-workspace-id $(az monitor log-analytics workspace show -g <rg> -n <workspace> --query customerId -o tsv) --logs-workspace-key "$(az monitor log-analytics workspace get-shared-keys -g <rg> -n <workspace> --query primarySharedKey -o tsv)"` for a workspace with the readers and the retention the company wants, instead of the generated one.
- **A WAF, Front Door or Application Gateway in front.** It adds a proxy, so set `MCP_TRUST_PROXY=2`, see Security notes. By default Front Door and Application Gateway send the origin's own host name, the generated `azurecontainerapps.io` one, to the origin. The server answers only for the host of `MCP_PUBLIC_URL`, so every path but `/health` then gets 403 with `Invalid Host` and the name it got, the health probe is green and nobody can discover, register or sign in. Either make the proxy forward the custom domain as the host header, with that domain bound on the app as above, or put the generated name in `MCP_ALLOWED_HOSTS`. `MCP_ALLOWED_HOSTS` only makes the server answer for that name. The browser still has to reach the origin of `MCP_PUBLIC_URL` through the proxy, since an approval on the consent page is checked against that origin and the cookies belong to that host. The start line does not name the allowed hosts, so check the first requests in the log.
- **Ingress IP restrictions** when only Claude Code connects, because it calls the server from the user's own machine: `az containerapp ingress access-restriction set -n fo-mcp -g fo-mcp --rule-name office --ip-address <your range> --action Allow`. Connectors in claude.ai and Claude Desktop connect from Anthropic's cloud, so such a rule shuts them out.
- **Static egress** when F&O or a firewall in front of it allows only known addresses. The outbound IPs of a Consumption only environment can change. A workload profiles environment with a NAT gateway on its subnet sends everything from one static IP.
- **Client secret in Key Vault** with a managed identity, as above, instead of a plain Container Apps secret.
- **Direct tokens and writes.** Off localhost the server accepts no tokens straight from Entra unless `MCP_ALLOWED_CLIENT_APPS` lists the apps they come from. List a test app only while you need it and never the server's own app. Apart from the holder of its secret, only public client flows on that app can produce its tokens. A device code phishing message could then turn them into access to `/mcp` past the consent page. Set `MCP_WRITE_ROLE` when writes are on. Off localhost the server warns at start when `MCP_ALLOWED_CLIENT_APPS` lists `FO_CLIENT_ID` and when writes are on without `MCP_WRITE_ROLE`.
- **HSTS.** With an https `MCP_PUBLIC_URL` every answer carries `Strict-Transport-Security: max-age=31536000`, so a browser that saw the server once keeps to https for a year. It has no `includeSubDomains`, so other hosts under your domain are not affected. On localhost, 127.0.0.1 and [::1] the header is left out. A browser keeps the policy per host name and not per port, so it would move every port of localhost to https for a year, the callback Claude Code signs in with included.

### Remote server notes

- `MCP_PUBLIC_URL` must be the URL Claude uses, with HTTPS once hosted. It is the OAuth issuer, the base of the callback redirect URI, the resource identifier in the metadata and the origin the consent page checks approvals against, so a mismatch shows up as a failed sign in. The MCP endpoint answers at the exact path of `MCP_PUBLIC_URL` only. A connector added with a trailing slash or another case of the path, for example `https://mcp.example.com/mcp/` or `/MCP` when the URL ends in `/mcp`, gets 404 and must be corrected.
- The server accepts redirect URIs on localhost, 127.0.0.1 and [::1] on any port (Claude Code, Claude Desktop, MCP Inspector) plus the claude.ai and claude.com callbacks. Any other client needs its redirect URI added to `redirectAllowed` in `src/oauth.ts`.
- An access token lasts as long as the Entra token behind it, about an hour. Then the client refreshes it and the server refreshes the Entra token behind it. A refresh token works for eight hours after it was issued, so a client that was idle for longer signs in again. When Entra cannot be reached the refresh answers 503 and the refresh token stays valid.
- A refresh token works once. Presented again within a few seconds (a parallel request) it returns the same new pair, presented again later it ends that whole sign in, because it was copied. That holds for every refresh token the sign in ever handed out, however many refreshes ago. A refresh token names its sign in and carries the server's signature, so none has to be stored to be recognised and a token cut short or changed names no sign in. Within those few seconds a copy of the token gets the new pair as well, so a stolen refresh token used that quickly goes unnoticed. That is the price of not signing a user out when two requests of one client race. A code used twice within its five minute lifetime ends the sign in it started. Later it is only an unknown code.
- A user holds at most 20 sign ins at a time, a new one ends the sign in refreshed least recently. The server keeps at most 5,000 sign ins in all. Each holds the user's Entra tokens, about 4 KB.
- Tokens straight from Entra are accepted too, for scripts and clients with their own app registration, but only from the apps on `MCP_ALLOWED_CLIENT_APPS`. Left empty that is the server's own app while `MCP_PUBLIC_URL` is on localhost or 127.0.0.1 and no app anywhere else. The start line says which applies. The token must have the audience `api://<client id>` or the client ID, the issuer and `tid` of the configured tenant, the `access_as_user` scope of a signed in user and an `oid`. App-only tokens are refused, there is no user to act for. A direct Entra token is accepted with up to five minutes of difference between Entra's clock and the server's in its `nbf` claim, as Microsoft's own libraries allow. A token past its `exp` is refused regardless.
- Every user gets their own metadata and legal entity caches and every MCP session belongs to the user who opened it. A user's cache keeps at most 200 entity definitions, the least recently used one goes first. Users who get the same entity list from F&O share one copy of it. Labels and enum definitions are shared, F&O gives every user the same answer for them. The server keeps at most 5,000 labels and 5,000 enum definitions, the least recently used one goes first. An entity list is refreshed after ten minutes. When the refresh fails because F&O or Entra could not be reached, answered 429 or 5xx or did not answer in time, the old list stays in use for 30 seconds and one line on stderr says so. Any other answer, such as a 401 or 403 for a user who may not read F&O any more, fails the call instead. An entity name that is not on the list is answered from the list with suggestions at once. The list is refreshed behind that answer at most every three minutes per user, so an entity deployed during a session shows up on the next call. Sessions without a request for an hour are closed. Past 10 sessions per user or 500 in total the least recently used one is closed.
- The sign in endpoints have limits per address and minute: 30 for `/authorize`, the consent form and `/callback`, 60 for `/register` and 300 for `/token` and `/revoke`. `/forget` counts under the limit of the consent form. `/mcp` takes 600 requests per user and minute. Over a limit the answer is 429 with `Retry-After`. A client `state` over 1,024 bytes goes back to the client as `invalid_request`.
- A cancelled tool call stops: requests in flight are aborted and a create or update that has not been sent yet is not sent. One that was sent already says that F&O may still have applied it.

The remote server has run against a personal tenant and a one-box, not against a company tenant. Not verified there are the consent policy such a tenant applies to the first sign in, where the authorized client and the Graph permissions in Entra setup follow Microsoft's documentation and not a run, a WAF, Front Door or Application Gateway in front of the ingress with the SSE stream of a session open through it, the sign in from the Claude mobile app and the image on Container Apps against a one-box with `FO_HOST_IP`. Try each on a test environment first and expect to adjust the steps above.

## Security notes

- `.env` holds the client secret. In a container pass it as a secret environment variable instead, from Key Vault when you can. It is in `.gitignore`, keep it out of version control and readable only by you (`chmod 600 .env`).
- The client secret expires. Note the date when you create it and rotate it before then, the server only needs a restart after you update `.env` or the secret. Without `MCP_STATE_KEY` the new secret also makes every MCP client of the remote server register again and every browser approve the consent page again, so set it before the first user signs in, see Hosting on Azure.
- Writes are off by default. With `FO_ALLOW_WRITES=1` the local server writes as the F&O user mapped to the client ID. The remote server writes as each signed in user with that user's own roles. The client ID mapping does not limit it. `MCP_WRITE_ROLE` limits the write tools to the users with that app role. Keep writes off on environments with real data.
- Everything the tools return is F&O data. A record can hold text written to steer the model, in a name, a note or a description. The server's instructions tell Claude that such text is data and never an instruction, but models do not reliably ignore instructions inside data. Never set your client to approve `create_record` or `update_record` without asking, read what Claude is about to write before you allow it. Do not use this connector in the same chat as email, web or other connectors that bring in outside text or send data out, also with writes off: text in a record can ask Claude to send what it read somewhere else. Limit what can be written with `FO_WRITE_ENTITIES` and who can write with `MCP_WRITE_ROLE`.
- `FO_INSECURE_TLS=1` turns off certificate checks for every request to F&O. Each of those requests carries an F&O token. Prefer `FO_CA_FILE`. When both are set, `FO_CA_FILE` wins and the checks stay on. The remote server refuses to start with it off localhost unless `FO_CA_FILE` is set, then the flag has no effect. Never set `NODE_TLS_REJECT_UNAUTHORIZED=0` instead, it turns the checks off for Entra too. Both servers warn about it at start, also when it comes from `.env`. The remote server refuses to start with it unless `MCP_PUBLIC_URL` is on localhost.
- No request to Entra or F&O follows a redirect. The token requests carry the client secret and, on behalf of a user, the user's token, which a redirect would send on to the host it names. A redirect fails the request with a hint to check `FO_AUTHORITY` or `FO_URL`.
- Every tool call writes one JSON line to stderr with the time, tool, entity, company, user, Entra object ID, client, MCP session, result, the first 200 characters of an error and the duration. Reads add `bytes`, the size of the answer Claude got. `query_entity` also adds `rows`, so bulk reads stand out. Writes add `sent` once the request went out, not when the connection to F&O could not be made, plus the key of the record and the names of the fields written. The key holds record values such as a customer account or a personnel number, which can be personal data. A write that went out and then ended in a timeout, a cancel, a restart, a broken connection or a gateway error has `outcome` set to `unknown`. Its `ok` is false, but F&O may still have applied it. Tokens, filters and query results are never logged and quoted values in error messages are masked. F&O error text can still name a value without quotes. `FO_AUDIT_VALUES=1` adds the written values, for an update also the old and the new values of the changed fields. `FO_AUDIT=0` turns the lines off. A call that the MCP SDK rejects before a tool runs, such as one with an unknown argument, leaves no line. `scripts/call.mjs` turns them off unless you set `FO_AUDIT=1`. The filter itself is never logged. For a read whose `filter` names `dataAreaId`, `company` therefore names the companies the filter limits the read to, for example `(from filter: DEMF)`. That holds only when every `dataAreaId` clause is a plain `eq` with a company ID and no `or` or `not` lets other companies through. Otherwise it reads `(from filter, not limited to DEMF)`, or `(from filter, no company named)` when no clause names one.
- Every request the remote server answered writes one line to stderr with the method, path, status, duration, client address, MCP session and user agent, in that order. The session is a dash for a request outside one and for a session ID the server did not accept. It is the same ID the audit line of a tool call carries, so a call in the audit log can be tied to the address and user agent of the request that made it. A request whose connection closed before the answer, the session stream a client drops included, leaves no line.
- F&O answers 429 when it throttles requests. The server waits once for a read when F&O sends `Retry-After`, never for a write. To keep Claude's load from crowding out other integrations, give it a low priority under **System administration > Setup > Throttling priority mapping**. The local server calls F&O as its client ID, map that with the type **Microsoft Entra application**. The remote server calls F&O as each signed in user. A mapping of the type **User** is identity wide. It lowers the priority of everything that person sends to OData, the Excel add-in, Power BI and Power Automate included, so use it for a dedicated group of users or not at all. An application mapping for the hosted server's app is only possible for an app listed under Microsoft Entra ID applications, which Entra setup tells you to leave out for a shared environment, because a mapped app's secret acts as the mapped user.
- The server sends one request per record and does not use OData `$batch`. A header and its lines are separate calls and not atomic, when a line fails the header stays.
- The per address limits of the sign in endpoints take the client address from `X-Forwarded-For`. Every proxy in front appends the address it got the request from, so behind `MCP_TRUST_PROXY` proxies (1 by default, for the Container Apps ingress) the client is that many entries from the end, with a port stripped. Entries further left come from the client and can be anything. A WAF, Front Door or Application Gateway in front of the ingress adds a proxy, so set `MCP_TRUST_PROXY=2` there. Hardening says what to do about the host header it forwards. Too low a number counts every user under the address of a proxy, so all of them share one limit. Too high a number lets a client choose its own address. An entry that is no IP address is not taken for one, the address of the connection counts then. Without a proxy in front set `MCP_TRUST_PROXY=0`, then the address of the connection counts. The start line names the setting and the request log shows the address each request was counted under, so check it after the first sign in.
- Anyone can register a client that calls itself Claude. The consent page shows the name the client chose and where the result goes. It asks users to approve only a connector they just added themselves. A remembered approval skips the consent page for 30 days, Microsoft's account picker then stands in for it. `/forget` withdraws the approvals of a browser.
- Keep the network security group rule for port 443 limited to your own IP addresses.
- The server honours `HTTPS_PROXY`, `HTTP_PROXY` and `NO_PROXY` for both Entra and F&O. Extra corporate root certificates go in `NODE_EXTRA_CA_CERTS`, which Node reads only when the process starts, so it has to be in the real environment and not in `.env`: an `"env"` block in `claude_desktop_config.json`, `claude mcp add -e NODE_EXTRA_CA_CERTS=...`, or the container's environment variables.

## How it works

`src/fo.ts` gets a token from Entra with client credentials or with the on-behalf-of exchange and calls the F&O OData endpoints. Entity names come from `/Metadata/DataEntities`, fields and keys from `/Metadata/PublicEntities`, enum elements from `/Metadata/PublicEnumerations` and label texts from `/Metadata/Labels`. `src/server.ts` registers the six tools with the MCP SDK. `src/index.ts` talks to Claude over stdio with one shared client. `src/http.ts` serves Streamable HTTP with one client per signed in user. `src/oauth.ts` is the OAuth front that signs users in with Entra: MCP clients expect dynamic registration, PKCE and a resource parameter of their choosing, Entra offers none of that, so the server is the authorization server from the client's point of view and Entra sits behind it.

Two F&O details worth knowing. OData only returns the user's default company unless `cross-company=true` is set. That is the default company of the mapped user in local mode and of the signed in user in remote mode, so the server always adds `cross-company=true` for company specific entities and scopes the query with a `dataAreaId` filter. And `$filter` has no string functions such as `contains` or `startswith`: string fields take only `eq` and `ne`, with a `*` wildcard inside the literal for a partial match, which the tool descriptions tell Claude up front.

## Tests and evals

`npm test` builds the server and runs 325 tests against a fake Entra and a fake F&O in the test process, no real environment needed. The evals go one step further: scenarios that run Claude Code headless against the same fake environment and check what reached F&O. See [evals/README.md](evals/README.md).

The tests make a certificate for the fake environment with `openssl`, which macOS and Linux have. On Windows run them in WSL, or with the `usr\bin` folder of Git for Windows on the PATH. Without `openssl` every suite that needs it is skipped with that reason and only 11 tests run. On Windows the four tests of a graceful shutdown on SIGTERM are skipped as well, since `kill()` ends a process there at once. So is the test of a stop through a process group. The evals stop the Claude Code CLI and the server it started through the CLI's process group. Windows has none, so there they use `taskkill /T`, which reaches the server only while the CLI still runs. The tests and the dry run of the evals pass on Windows with Node 22.19 and Node 24.
